# Web 全链路功能分析

## 适用范围

用户指定一个 Web 业务大类或子模块，需要梳理其功能点及前端到后端基础设施的完整链路时使用。

输入通常包括：业务大类、可选页面/子模块、关注的服务或功能。若下游仓库不可访问，只记录可证明的边界，不推测内部实现。

## 不变原则

1. 以用户可感知的业务行为拆分功能，不按组件或接口数量机械拆分。
2. 以真实源码、配置、接口契约和知识图谱定位结果为证据；不能用名称推断服务、表或 Topic。
3. 核心功能必须继续追踪到 DAO/Repository、缓存和 MQ 消费端，直到数据落点或明确的异步边界。
4. 主链路图只画关键节点；字段、条件、错误码和代码位置放在表格中。
5. 不执行运行态验证，不把“已验证”作为静态文档状态；不修改业务代码。
6. 业务大类 README、服务依赖图和资源目录只是汇总，不得替代单功能完整链路。
7. 依赖服务名称不是追踪终点；必须继续检查当前可访问的客户端、路由、Handler、Service、DAO/Repository、缓存和 MQ。

## 精简分析方法

```text
识别入口 → 建立候选功能 → 逐层追踪源码 → 调整功能边界
→ 输出功能卡片和图示 → 更新索引
```

- 先建立候选清单，完成源码追踪后再确定最终拆分。
- 多个小动作如果入口、状态和结果一致，可以聚合为一个稳定能力域；不要按组件或接口数量机械拆分。
- 被多个业务复用的内容单独沉淀为共享能力，业务功能只记录引用关系和本功能的使用方式。
- 知识图谱只用于定位，最终结论必须回到源码、配置或接口契约；源码不可访问时只记录最后可确认的边界。

## 深度追踪门槛

### 功能点粒度

一个功能点应对应一个用户可感知的行为或独立自动动作。不同入口、权限边界、状态流转或结果对象通常需要拆分；如果多个小动作共享入口、状态和结果，可以聚合为一个稳定能力域。


### 分层追踪顺序

每个功能必须按以下顺序逐层确认，不能先写服务依赖总览再反向补链路：

```text
前端路由/入口
→ 组件事件
→ Store/Composable 方法
→ API 封装、请求参数、响应结构
→ Web Router
→ Middleware/鉴权/灰度
→ Handler/Controller
→ Service
→ Client/RPC/HTTP 调用
→ 下游服务入口与业务方法
→ DAO/Repository/DB、Redis、MQ Producer
→ MQ Consumer 及后续数据变化
```

每一层都要记录“已找到的代码证据”或“明确不可访问的边界”。不能因为找到了下游服务名，就把后续层级写成已确认。

### 完整链路判定

功能只有同时满足以下条件，才能标记为“源码链路已确认”：

- 前端入口、调用方法和请求参数已确认；
- Web 后端 Router、Middleware、Handler、Service 已确认；
- 关键下游 Client 及服务端方法已确认；
- DB/Redis/MQ 读写已确认，或明确证明该功能不涉及该资源；
- 发现 MQ Producer 时，已搜索 Consumer；
- 外部服务无法继续追踪时，已在“依赖边界”中写明最后可确认层级。

仅完成前端到 BFF、或仅完成服务依赖识别时，最多标记为“接口链路已确认”。

### 核心源码流程

核心功能必须增加“核心源码流程”章节，按一次真实请求的执行顺序串联：

```text
前端触发 → API → Middleware/Handler → Service → 下游调用
→ 数据/缓存/MQ → 条件分支 → 结果组装 → 前端返回
```

每一步写明源码文件、函数、关键字段和结果变化。时序图只表达关系，不能替代这段源码流程；普通功能可使用简化版。

## 工作流程

### 1. 识别功能点

从前端扫描 `pages/routes/layouts`、`components`、`composables`、`stores`、API 封装、middleware/plugins、菜单入口和功能开关。

按业务行为建立稳定 ID，例如 `{DOMAIN}-001`，识别：

- 页面级功能：进入页面、初始化、加载历史；
- 操作级功能：发送、编辑、删除、重试、选择、提交；
- 自动触发功能：初始化补偿、异步刷新、缓存更新。

先建立候选功能清单并记录入口，再逐功能追踪；追踪过程中允许调整功能边界，确认后再更新 `overview/feature-index.md` 和正式文档。不能只用一个“大类功能”占位后直接生成汇总文档。

核心功能追踪完成后，先整理一次请求的源码执行顺序，再生成时序图和功能卡片，避免只有调用关系而没有执行过程。

### 2. 追踪前端和 BFF

按以下顺序确认代码关系：

```text
页面/路由 → 组件事件 → Store/Composable → API 封装
→ Router → Handler → Service → Client/RPC
```

记录真实文件、方法/符号、请求参数、响应结构、鉴权、开关、参数转换、聚合、缓存、SSE/WebSocket、超时、重试和取消逻辑。

### 3. 追踪下游服务

沿 `Client → 服务入口 → Service → DAO/Repository/Cache/MQ` 下钻。只追踪影响当前功能结果的业务代码；忽略通用日志、监控、埋点和无关基础组件。

如果下游服务仓库可访问，必须继续读取其业务实现；如果只有客户端或 UA 图谱，必须把结论限制在客户端契约，并记录“下游服务实现不可访问”。不得用服务名、接口名或常见架构习惯补写内部实现。

### 4. 追踪数据和异步链路

对每个功能明确：

- DB：表、读写操作、关键字段、关联键、事务边界；
- Redis：Key 模式、读写、锁、TTL、失效和用途；
- MQ：Topic/Event/Tag、Producer、Consumer、触发时机、消息字段、消费后的 DB/缓存变化、幂等/重试/死信。

发现 Producer 后继续搜索 Consumer；无法从当前源码确认的消费端，记录“证据边界”，不要写成已完成链路。

## 文档归档规则

功能点放在业务大类目录；数据库表、线上库名和分库分表说明优先合并到根级统一文档，用标题区分业务域：

```text
features/{中文业务大类}/
├── {ID}-{中文功能名}/README.md
└── README.md

database/
└── 业务表与分库分表.md
```

例如某个业务大类：

```text
features/{业务大类}/
├── {DOMAIN}-001-{功能名}/README.md
└── {DOMAIN}-002-{功能名}/README.md

database/业务表与分库分表.md
```

跨多个业务大类复用的数据库说明放在根级 `database/`；文档内按“线上库总览→分库分表规则→业务域→表反查”组织。接口、服务、MQ、缓存仍按现有资源目录维护。

### 业务大类目录命名

业务大类下的一级能力目录统一使用：

```text
{两位序号}-{中文能力域}/
```

示例：`features/{中文业务大类}/{两位序号}-{中文能力域}/`

目录名不带功能 ID、不使用 API/服务名、不使用实现细节；功能 ID 放在能力目录 README 标题和全局功能总表中。多个小功能可以聚合到一个稳定能力域，不能为了追求细粒度把目录拆成接口清单。

## 必须产出的图

核心功能至少包含以下图，均使用 Markdown 中的 Mermaid 源码：

1. 功能地图：`flowchart`，只画业务大类→子模块→功能点。
2. 单功能时序图：`sequenceDiagram`，画真实同步/异步调用、关键分支和失败边界。
3. 服务依赖图：`flowchart LR`，画前端→BFF→下游服务及主要依赖。
4. 数据关系图：`erDiagram`，只画源码确认的核心表和关键字段。
5. MQ 事件图：`flowchart LR`，画 Producer→Topic→Consumer→数据变更；没有 MQ 时不强行绘制。

### Mermaid 兼容性规则

- 参与者使用简单 ASCII ID，例如 `FE`、`BFF`、`SM`、`DB`、`MQ`；中文和复杂服务名只放在 `as` 标签中。
- 时序消息优先使用 `->>`、`-->>`；不要使用可能被旧渲染器拒绝的 `-)` 异步箭头，用 `[异步]` 文本表达异步语义。
- `Note` 使用简短纯文本，避免在 Note 中使用复杂表达式、分号和特殊符号。
- 关键字段关系写在图下方表格中，避免把过长 SQL、JSON 或表达式塞进图中。
- 如果当前环境提供 Mermaid MCP，先识别其实际工具和参数再调用；不可用时只做源码级 Mermaid 语法检查，不声称已完成渲染校验。

## 功能卡片最低结构

每个功能创建 `features/{大类}/{ID}-{中文名称}/README.md`，至少包含：

1. 功能概述和元数据；
2. 核心源码流程；
3. 端到端时序图；
4. 前端链路和代码证据；
5. BFF 与下游服务链路；
6. DB/Redis 读写表；
7. MQ 生产和消费表；
8. API 契约；
9. 异常、超时、取消、重试、幂等和异步边界；
10. 源码证据和被哪些功能复用的资源索引。

关键字段应根据业务实际识别，至少关注业务主键、跨表关联键、状态字段、时间边界字段和幂等字段；不要把某个业务域的字段清单固化为所有功能的通用规则。

## 状态和证据

### 功能状态

- `已登记`：已识别功能入口。
- `接口链路已确认`：前端入口、API 和 BFF 边界已确认。
- `源码链路已确认`：下游服务、数据读写和 MQ 消费边界均有证据。

功能状态不能由 README 或服务依赖图单独决定，必须以对应功能卡片的逐层证据为准。

### 证据等级

- `L1`：源码文件、方法、结构体或调用关系。
- `L2`：配置、YApi、Proto、服务注册或 Topic 配置。
- `KG`：知识图谱定位结果，关键结论仍需源码或配置支撑。

每条关键结论记录仓库、文件路径、方法/符号和行号；不把没有证据的字段、消费者或事务关系写成确定事实。

## 交付检查

- 功能总表已更新，功能 ID 唯一且链接有效；
- 功能点已按用户行为拆分，没有用一个大功能覆盖多个独立动作；
- 前端入口、BFF、下游服务和核心 DAO 均有代码证据；
- 每个“源码链路已确认”的功能都完成了分层追踪门槛；
- 每个核心功能都包含按源码执行顺序编写的“核心源码流程”；
- DB/Redis/MQ 只记录当前功能实际涉及的资源；
- MQ 已尽量追踪到消费者和后续数据变化；
- 核心图使用兼容 Mermaid 语法，图中文字与表格结论一致；
- 功能专属资源已归档到对应中文业务大类；
- 已更新服务、API、表、Redis Key、Topic 的反向索引；
- 未把推测内容标成源码已确认，未加入运行态验证环节。
